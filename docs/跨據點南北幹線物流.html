00 背景與問題

既有物流子系統設計以「單一據點內、10 個固定停靠站」為範圍。本次新議題處理更大尺度的情境： 公司在台灣約有 10 個據點（例如桃園龍潭、台中、高雄左營、台南等），車輛需要跑一趟涵蓋多個據點的 南北向路線，沿途在多個據點收貨、卸貨，目標是最大化車輛利用率、減少空駛。

這 10 個據點在地理上恰好呈南北一直線分佈，因此「固定據點順序」與「南到北 / 北到南」是同一件事， 不需要額外的排序判斷邏輯。

出發據點（例：桃園龍潭） │ 去程 → 依南北固定順序，逐據點檢查是否收送貨 ├─ 台中據點：卸部分貨、裝新貨（視當下剩餘容量） ├─ … └─ 終點（系統自動判斷，例：高雄左營 或 台南） │ │ （去程與回程間隔：待確認） ▼ 終點據點 │ 回程 → 依南北固定順序（反向），逐據點檢查是否收送貨 ├─ … └─ 回到原出發據點（固定，不做提前結束判斷）

01 範疇界定

✓ 本次討論範圍內
  • 單一車輛、單趟南北幹線的收送貨與終點判斷邏輯
  • 去程 / 回程的容量與時間規則
  • 據點層級的路由（不含據點內建物排序）
✕ 排除於本次討論之外
  • 據點內部建物收送貨順序（交由司機臨場判斷）
  • 同一天多台車輛之間的貨物分配 / 加開班次判斷
  • 車輛－班次的每日指派（沿用既有：調度室人工設定）

02 已確認決策

2.1　據點內部處理方式

決策
車輛進入據點後，不做站內建物排序，直接依系統提供的「建物收送貨清單」由司機自行決定拜訪順序。
系統的最小排程單位到「據點」為止，據點內部順序對整體效率影響小，避免過度設計。

2.2　跨據點路由順序

決策
10 個據點依實際地理位置（南北向）排出固定順序表，車次依此順序（南→北 或 北→南）行進，沒貨的據點跳過，不做動態排序最佳化。
與既有物流子系統「10 個固定停靠站、固定順序」原則一致，僅將單位從「站」擴大為「據點」。

2.3　終點自動判斷

決策
這趟車最遠跑到哪個據點，由系統自動決定（非調度室事先人工指定），調度室僅在系統判斷出現例外狀況時人工介入。 判斷邏輯採貪婪法：依南北固定順序逐據點檢查。
沿用共乘子系統「MVP 用貪婪規則引擎，不用 VRP 求解器」的原則，確保邏輯可解釋、調度員可一眼看懂系統為何選了這個範圍， 也符合「只在有問題才介入」的期待。
待業務單位覆核 · 2.3 修訂　終點延伸規則調整
容量與時間對終點的作用不對等，需分開描述（工程端實作回填，尚未經業務單位覆核）：
・容量觸頂 → 不停止延伸：某站待裝的表單放不下時，僅該張表單跳過（留待下一班次，見 2.5），車輛仍繼續依序往下一據點前進，因為後續據點可能有卸貨動作釋出空間、也可能有更小的貨可收。
・總計時間觸頂 → 停止延伸：累積時間（行駛＋裝卸，見 2.6）超過上限時，終點不再往外擴。
・終點的實際取值＝本趟所有已裝載表單之送貨據點中最南（最遠）者。若某據點只是路過、沒有任何已載貨物要送到該站，該站不會成為終點。
異動原因：原條文寫「容量或時間任一先觸及上限即停止延伸」，實作時發現容量滿即收工會提早截斷路線，讓後段本來可服務的據點失去服務機會，違背 2.4 動態淨值的用意。故修訂為：只有時間是延伸的硬上限，容量只影響單張表單能否上車。
待覆核原因：此調整改變了原本已與業務單位確認過的「容量或時間先到者為準」規則，屬於工程端單方面回填的修正，尚未經業務單位重新確認是否認可此邏輯調整。

2.4　容量判斷基準

決策
容量以「目前車上實際載貨量」（動態淨值）為準，卸貨後釋出的空間可立即被後續據點的新貨佔用，不採計歷史最高累積載貨量。
若不採計卸貨釋出的空間，「中途卸貨再裝貨」將失去意義，車輛可延伸範圍會被低估，違背最大化利用率的核心目標。

2.5　容量不足時的處理（部分裝載）

決策
當某站待裝貨量超過剩餘可用空間時，採部分上車：能塞多少算多少；拆分的最小單位是整張申請表單，不拆表單內的貨物線項。 同一站有多張表單待裝載時，依核准時間排序，逐張檢查能否完整放入剩餘空間，放得下即裝載，放不下則跳過、留待下一班次。
整批打回會嚴重犧牲填載率；但拆表單內線項會讓同一筆申請的貨物分批到貨，增加申請人困惑與異常追蹤複雜度，故以整張表單為最小單位。

2.6　時間上限的計算方式

決策
總計時間 = 累積行駛時間 + 累積各站裝卸貨時間，沿用既有「各站裝卸貨時間自報並加總」機制。
僅計算行駛時間會嚴重低估實際耗時，導致終點判斷失準、影響司機工時安排。

2.7　回程規則

決策
回程終點固定回到原出發據點，不做「回程自動判斷提前結束」；回程沿途的收送貨邏輯與去程完全相同 （依南北反向固定順序，逐站檢查容量與時間，貪婪法能塞則塞）。
與既有共乘子系統「多天派車最後一天強制回到基地」原則一致，避免車輛／司機停留在無法管理的中途據點。

2.8　多車協調（範疇外）

決策
本次僅處理單一車輛的邏輯；「同一天多台車如何分配貨物 / 是否加開班次」列為下一階段獨立議題，不在本次範圍內。
車輛－班次每日指派本來就是調度室手動設定；多車協調涉及是否加開班次等更高層營運決策，複雜度層級不同，應獨立討論。

2.9　行駛時間與時間上限的參數基準（已由業務單位提供實際資料，本版更新）

決策（更新）
2.6 只定義了「總計時間 = 行駛 + 裝卸」的公式，未定義計算所需的參數。原版採示意常數， 業務單位現已提供實際資料，改採下列基準：
・據點間行駛時間：改採業務單位提供之「10 據點相互路程表」查表取值，不再使用單一常數乘以段數。此表同時涵蓋龍潭、屏東、高雄三處休息會館之位置，供 2.13 計算「返回休息地」時間使用。
・每日出發時間：不再是固定值，改由「司機實際上班時間 + 前置作業」推算（詳見 2.13）；排班階段一律以表定上班時間 08:00 為規劃基準。
・每日總時間上限：12.5 小時（涵蓋範圍詳見 2.13）。
改為查表後，行駛時間反映各據點對之實際差異，不再因單一常數而失真；每日上限有了明確數值與涵蓋定義，2.3 的「時間觸頂才停止延伸」才有可驗算的依據。

2.10　容量判定的層級（回填自實作）

決策
南北幹線的容量判定只採 Level 1（有效體積，含類別浪費係數與形狀懲罰）＋ 總重量上限， 不執行區域內物流所用的 Level 2 單品六方向維度檢查。
幹線一趟會跨多個據點、反覆卸裝，同一台車的裝載狀態變化次數遠高於區域內單趟路線；逐站重跑 Level 2 的成本與收益不成比例。 風險是「單件超長貨物體積過關但實際塞不進車廂」——此情境由據點端收貨時人工目視把關。此為與區域內物流刻意不一致之處，非疏漏。

2.11　交貨時間門檻（回填自實作）

決策
託運單新增「交貨時間」欄位（可不填，不填即不設限）。派車時作為硬性門檻：
・直達車：預估抵達目的地時間 = 出發時間 + 起訖據點間距 × 段行駛時間；若晚於交貨時間，該單不上這班，留待下一班直達車。
・非直達車：於裝貨當下估算送達時間 = 出發時間 + 已累積時間 + 本單裝貨時間 + 本站至送貨據點的行駛時間；若晚於交貨時間，整張表單跳過，留待下一班次。
未通過門檻的處理方式與 2.5 容量不足一致（留待下一班次），不另立狀態。
原規格只用容量與總時間上限決定誰能上車，沒有任何機制保障「這批貨幾號前一定要到」。缺了這道門檻，急件與一般件在派車時完全等價，實務上會出現先到先載但晚到的情況。

2.12　司機休息與用餐規則（業務單位提供）

決策
業務單位提供之休息／用餐排程表，依累積行駛時間觸發：
累積行駛時間門檻觸發項目耗時
超過 3 小時第一次休息0.5 小時
超過 4 小時第一次用餐1 小時
超過 6 小時第二次休息0.5 小時
超過 8 小時第二次用餐0.5 小時
超過 10 小時第三次休息0.5 小時
判斷規則：
・觸發基準為純累積行駛時間，不含休息、用餐、裝卸貨時間（避免休息時間反過來觸發下一次休息的循環邏輯）。
・五個門檻共用同一條不歸零的累積時數線，達到節點即依序觸發，不會因觸發過休息而重新起算下一個門檻。
・累積時數每天出勤重新歸零，隔夜過夜視為已充分休息，不延續前一日累積。
・觸發後產生的休息／用餐時間，計入當日 12.5 小時總時間上限（見 2.13），會壓縮當日可用於行駛與裝卸的時數。
休息與用餐屬司機生理需求與法規要求，必須佔用當日在勤時數；若不計入上限而允許無限加時，2.9 的每日總時間上限將形同虛設。

2.13　每日總時間上限 12.5 小時的組成

決策
每日總時間上限為 12.5 小時，係「司機當日從上班到下班的完整在勤時數上限」，涵蓋以下全部項目，無任何一段不計入：
・待勤——自司機實際上班時間起算，即使空等未執行任何作業也照計。
・出勤前緩衝——車輛檢查、前往報到。
・裝貨、開車（行駛）、卸貨。
・休息與用餐——依 2.12 規則觸發之時數。
・收工後緩衝——車輛檢整、返回休息地。其中「返回休息地」非固定常數，須依當日收工位置查 2.9 據點路程表計算至最近休息會館（龍潭、屏東、高雄）之時間。
上班時間採彈性緩衝制：表定 08:00，司機可於 07:30–08:30 之間到班；12.5 小時額度自司機實際到班時間起算 （07:30 到班者當日硬性收工時限為 20:00，08:30 到班者為 21:00）。
本項實質修正了 2.6「總計時間 = 行駛 + 裝卸」的公式——該公式並不完整，遺漏了待勤、前後緩衝與休息用餐等同樣佔用司機在勤時數的項目。 以完整組成計算，2.3「時間觸頂才停止延伸」的判斷才會貼近實務。

2.14　媒合截止時間

決策
貨物媒合作業於派車日前兩天中午 12:00 截止。截止後送出的申請單，系統自動排入下一個可媒合的車次，不接受插單； 急件需求則透過 2.11 交貨時間門檻機制篩選，或由調度室人工介入處理例外。 因媒合須提前兩日完成，排班階段無從得知司機當日實際到班時間，故一律以表定 08:00 為規劃基準； 實際到班時間造成的 ±30 分鐘差異，屬調度室事後例外處理範圍，不回頭影響已排定的媒合結果。
處理方式與 3.5「被排擠的非直達貨物自動順延」一致，不另立新狀態；以表定時間規劃可讓派車計算在事前完成，且據點間行駛時間遠大於 30 分鐘，到班差異通常不影響據點層級的終點判斷。

2.15　容量參數的取值來源

決策
2.4、2.10 的容量判斷（Level 1 有效體積＋總重量上限），其容積與載重上限直接取自既有車輛主檔的個別車輛參數， 不另行維護「車型 → 容量」對照表。
亦即派車時取的是「這台車的容量」而非「這個車型的容量」；容量判斷的邏輯本身不變，僅取值來源明確化。
車輛主檔已存在且已掛載容積與載重欄位，同車型不同車款的規格未必一致，逐車取值較依車型取值精確， 且免去額外維護一張對照表。此項使容量參數與 Q3「車型決定方式」脫鉤——車型未定不影響容量判斷可運作。

03 天數表與直達（急件）規則

本節原以「天數會因是否中途停靠而不同」為前提設計。業務單位後續澄清： 最短天數表已內含所有變數，中途停靠與否不影響天數——中途要不要順路收貨，純粹取決於 12.5 小時額度塞不塞得下。 因此「直達」的性質也隨之改變，本節已依此修訂（見 3.1、3.2）。

3.1　最短天數表的性質（本版修訂）

決策（修訂）
天數是「整台車」的屬性（不是單張申請表單各自的屬性），由業務單位提供對照表內容，系統只負責查表，不自行推算。 天數指的是「去程＋回程」整個出車週期的總天數：2 天＝去程當天到達目的地並過夜、隔天回程； 3 天＝去程本身跨 2 天才到達最遠據點、第 3 天才回程。目前已知最大天數為 3 天。
本版修訂：對照表不再拆成「直達／有停靠」兩張，改為業務單位提供之 「各據點出差最短天數表」，依「車型（大車／小車）× 目的地據點」查表 （例：小車龍潭→民雄固定 2 天）。中途有無停靠收貨不影響天數。
天數表為寬鬆估計值，非精算值，僅作為調度室與司機的排班參考資訊（安排過夜、通知等）， 不參與運算、不反過來限制 12.5 小時精算結果。急件直達亦照表計算、不會縮短天數—— 表本身即為「最短」天數，直達影響的是這趟車能順便服務多少貨，而非總天數。
若實際精算耗時超出表定天數（業務單位認為此表寬鬆，應不常見）：以精算為準照常派車， 但於調度室介面標示「本趟預估天數超出表定值」提醒調度員（沿用 3.8 機制），不由系統擋下或強制截斷路線。
出勤天數綁定車輛／司機排班，是整趟出車的屬性而非個別申請單屬性。 原設計以「是否停靠」拆兩張表，係基於停靠會拉長天數的假設；業務單位澄清後該假設不成立，改依車型維度即可。 天數表與 12.5 小時精算各司其職：前者是寬鬆的排班參考，後者才是決定終點與收貨量的硬性依據，兩者不互相驗證，避免寬鬆值否決精算結果造成貨物無謂延誤。

3.2　直達的兩種來源（本版修訂）

決策（修訂）
「直達」有兩種來源，性質不同，需分開處理：
・申請人指定的直達（急件）——屬使用者需求，是派車的輸入條件。申請人填單時勾選， 即使 12.5 小時額度塞得下中間站，只要有這張單，車輛仍必須放棄中途收貨。 此類直達即獨立派一台車，不論貨量多寡，不湊單、不與其他非直達貨物併車；一台直達車只服務單一目的地據點。 3.3～3.10 的分流邏輯適用於此類。
・自然直達（時間不足導致）——屬排程結果而非使用者需求。車輛本可順路收中間站的貨， 但 12.5 小時額度塞不下，因而未停靠任何中間站。 此類不需勾選、不觸發獨立派車，也不套用 3.4 的回程全域直達檢查，僅是事後的狀態描述。
業務單位澄清後，「時間塞得下就順路收、塞不下就沒停靠」是排程的自然結果，不應與使用者主動要求的急件混為一談。 兩者若不分開，會導致系統為了單純的時間不足而誤觸發急件等級的獨立派車與回程鎖定，造成不必要的運能浪費。

3.3　直達車的容量與終點邏輯

決策
直達車全程不卸貨，容量只會單向被佔用，不會有中途卸貨釋放空間的動態變化。 因此直達車不套用既有的貪婪法終點判斷邏輯，終點即為申請單指定的目的地； 系統僅需依核准時間排序，將同終點的直達申請單依序累加貨量，直到容量上限，超過的部分留給下一班直達車。
貪婪法「沿線逐站累加＋卸貨釋放空間」的前提是中途有卸貨動作，直達車不存在這個前提，改用單純容量加總檢查即可，邏輯更直接。

3.4　回程的全域直達檢查（適用所有車輛）

決策
不論去程車種為何，任何一台車的回程都要先檢查：回程實際會經過的路段上， 是否存在「有效、待處理、且時間上會撞期（同一天／同一班次內）」的申請人指定直達（急件）申請單。 若有，回程該路段須鎖定為直達模式，不能中途停靠收送其他非直達貨物；若無，回程可比照停靠車邏輯正常沿路收送非直達貨物。
本版補充：此處檢查的對象僅限申請人指定的急件直達單；3.2 所述的「自然直達」（時間不足導致未停靠）不觸發本項鎖定。
直達需求優先權須貫穿全部車輛與去回程，才能確保「直達＝不繞路」的承諾不被其他非直達貨物的合併需求打破；同時檢查路線＋時間窗可避免系統過度保守、永久鎖死某條路線。

3.5　被排擠的非直達貨物

決策
因回程被鎖定為直達模式、而無法搭上這趟車的非直達申請單，系統自動順延安排到下一趟符合條件的車次處理。
直接沿用既有物流子系統「班次貨量已滿、自動順延下一班次」的既有機制，不需另立新規則、也不需另外派車。

3.6　回程被迫鎖定直達的容量與終點邏輯

3.4 定義了「回程何時要鎖定直達」，但沒有定義「被鎖定的這台車，容量與終點該套哪一套規則」—— 這台車原本是非直達車、正在用動態淨值容量邏輯運作，回程途中才被撞期的直達需求鎖定， 跟一開始就是直達車（3.3）的情況不完全一樣，需要額外釐清。

決策
回程被迫鎖定直達的車輛，容量計算延續原本的動態淨值邏輯（2.4），不切換成 3.3 的純容量加總； 終點依然是出發據點（回程本來就固定回基地）；鎖定直達的實際效果僅止於「途中不再收新的非直達貨」， 沿線據點若剛好沒有撞期的直達貨可收，車輛仍正常依序經過，不影響其回到基地。
鎖定直達改變的是「能不能收新貨」，不是這台車從出發以來的容量計算方式；容量邏輯若因鎖定而回頭切換，會造成同一趟行程中途變更計算基準，徒增系統與稽核複雜度。

3.7　四模式決策矩陣

彙整目前所有已定案情境的容量計算方式與終點判斷邏輯，確認沒有未定義的行為。 本表中的「直達」均指 3.2 所述「申請人指定的直達（急件）」；自然直達（時間不足導致未停靠）不屬獨立模式， 其容量與終點邏輯與「非直達」列相同，僅實際結果上未停靠任何中間站。

調度室操作介面需明確顯示每台車目前的派遣模式（直達 / 非直達 / 回程被迫鎖定直達）與觸發原因。
疊加直達分流（3.2）與回程動態鎖定（3.4）後，單看貪婪法邏輯已不足以讓調度員一眼判斷車輛狀態；補上模式標示才能維持 2.3 原本「可解釋、易覆核」的設計初衷。

3.9　直達車派車的成本前提

決策
「有直達申請即獨立派車，不論貨量多寡」是業務既定政策——直達本身即是一種服務承諾（類似專送／急件），成本已內含於服務定義中，不需要工程單位另外覆核合理性。
避免將既定的業務服務設計誤判為工程單位字面推導出的邊界案例，維持業務與系統認知一致。

3.10　多據點同時派車的優先序

決策
回程車行經中途據點時，若該站有貨要送，優先判斷這台回程車是否還有剩餘容量可以承載——能載即由這台回程車順路收送， 不需要因為那是「別的據點」而另外從當地派車；只有當回程車容量不足以承載時，才屬於需要多車協調（下一階段議題）處理的情境。
此優先序判斷仍是圍繞單一車輛自身容量的決策，不需要跨車輛的即時排程資訊互通，因此可先行定案，不必等待下一階段的多車協調機制。
