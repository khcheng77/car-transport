## 0. 使用方式（給操作者）

1. 將本檔（PLAN.md）與三份原始 HTML 報告放入專案根目錄的 `docs/` 下。
2. 在專案根目錄建立 `CLAUDE.md`（範本見附錄 A），讓每次工作階段自動載入技術前提。
3. 逐階段執行，每次指派一個任務編號，例如：

   ```
   請閱讀 docs/PLAN.md，執行 Phase 1 的 T1-2，完成後跑驗收條件並回報結果。
   ```

4. 每個 Phase 結束後執行該階段的「驗收檢核」，通過才進入下一階段。
5. 環境為隔離內網：**產出程式碼不得引用任何外部線上服務**（地圖 API、CDN、NuGet 還原以外的網路呼叫）。開發機產生的程式碼須可在無網路環境編譯執行。

## 1. 技術前提（全域約束）

| 項目 | 約束 |
|---|---|
| 框架 | C# / .NET Framework 4.8 / ASP.NET MVC（**非** .NET Core、非 Web API 獨立層） |
| 相依注入 | **不使用 DI 容器**。共用 Provider 一律 static 單例，內部自行讀取設定檔取得連線字串 |
| 前端 | MVC Razor + JavaScript（沿用既有系統慣例，不引入 SPA 框架） |
| 資料庫 | 既有 MIS 資料庫（SQL Server 假設），新增資料表以 `VD_` 前綴命名 |
| 外部整合 | 僅一項：司機休請假系統 API（內網）。**不串外部地圖 API** |
| 併發 | 載運量不高，**不做併發扣容量的鎖定／交易隔離機制**，Repository 單純讀取／判斷／寫入 |
| 通知 | SMTP 內網寄信（物流異常回報、共乘逾期作廢兩處使用） |
| 演算法選型 | 一律貪婪規則引擎，**不用 VRP 求解器、不做 3D 碰撞模擬**，邏輯必須可解釋、可人工覆核 |

## 2. 系統分區總覽

```
車輛派遣系統
├── 共用基礎層（Phase 0–1）
│     主檔（據點/站點/建物/車程表/係數表/車輛/司機）
│     裝載判定引擎（Level 1 + Level 2 + 類別浪費係數 + 重量）
│     兩層審批流程、資源可用性檢核（保修/請假/當前位置）
│
├── 模組 A：區域內物流貨運（Phase 2–3）
│     10 站固定路線、班次排班、收貨時間模式、駕駛異常回報
│
├── 模組 B：跨據點南北幹線物流（Phase 4）
│     貪婪終點判斷、直達/非直達分流、回程直達鎖定、天數對照表
│
└── 模組 C：差旅派車自動媒合（共乘）（Phase 5）
      來回單/單程單、批次媒合按鈕、手動併車、逾期作廢
```

資源池原則：**物流（A+B）與商務共乘（C）的車輛/司機資源池完全分開，互不搶用。**

## 3. 不可違反決策清單（Guardrails）

Claude Code 在任何任務中都不得違反以下定案。若發現實作上有衝突，**停下來回報，不得自行變更**。

### 3.1 裝載判定（模組 A/B 共用）
- G01　僅用 Level 1（體積加總）+ Level 2（單品六方向旋轉維度檢查），**不做 Level 3 碰撞模擬**。
- G02　輔以地板面積瓶頸法 + 長寬比形狀懲罰係數。
- G03　浪費係數依「貨物類別」查表：資料庫儲存、記憶體快取、查無類別用保底預設值、不中斷流程。
- G04　係數 Provider 為 static 單例，不用 DI。
- G05　重量為第二維度：車輛總重量上限，逐站累計（卸扣、收加）加總比較，**不做單品重量檢查**。

### 3.2 區域內物流（模組 A）
- G10　「最近的一台車」＝**時間軸最近的下一班次**，與空間距離無關。
- G11　媒合為**同步等待結果**；迴圈終止條件＝當日最後一班仍裝不下（無 maxAttempts）。
- G12　當日排不進去：**不留候補、不排隔日**，提示「請明天請早再試」。
- G13　一張申請單＝一個目的地，可多筆貨物項目；多站巡迴靠固定路線，不靠一單多站。
- G14　目的地兩層階層選單（站點→建物），路線固定 10 站、固定地理順序、無貨跳過、不重排。
- G15　同站先卸貨後裝貨；上下貨時間申請人自填，同站多單**加總**。
- G16　同站多單依**審核通過時間**排序判定時間額度，額度不足的單被跳過（以單為單位）。
- G17　被跳過的單**自動順延**下一個經過同站的班次；當天最後一班仍不行→即時提醒使用者改期。
- G18　路線與車輛分組對應，「今日哪台車跑哪班次」**人工每日排定**，系統只記錄對應並代入容量參數。
- G19　收貨時間二選一：「指定期望時間」（找到站時間差最小的班次，早晚都比）或「越快越好」（找最早排得進去的班次）。兩種模式**都不享班次內插隊優先權**，班次內一律依審核通過時間。
- G20　駕駛異常回報：跑完整趟回總部後才回報、只標異常站點、記錄到**申請單層級**、存檔＋**立即**自動寄信給申請人＋直屬主管（沿用審批對應關係，不另建表），一單一信。不做「顯示於申請畫面」。

### 3.3 南北幹線（模組 B）
- G30　10 個據點南北一直線，固定順序表，無貨跳過，不做動態排序。
- G31　據點內建物順序不排，司機自行決定，系統只給清單。
- G32　非直達車終點由系統貪婪法自動判斷：容量或總計時間任一先觸頂即為終點。
- G33　容量以**動態淨值**（目前車上實際載貨量）為準，卸貨釋出空間可再用。
- G34　部分裝載：能塞多少算多少，最小單位＝**整張申請表單**，不拆單內線項；同站多單依核准時間逐張檢查。
- G35　總計時間＝累積行駛時間＋各站自報裝卸時間加總。
- G36　回程固定回原出發據點，收送貨邏輯同去程（反向）。
- G37　天數為**整台車屬性**，查業務單位提供的兩張二維對照表（直達表／有停靠表），系統只查表不推算，已知最大 3 天。
- G38　直達分流：申請人勾選直達／非直達；當天有直達單即**獨立派車**（不論貨量、不湊單、單一目的地）。此為業務既定政策，不覆核合理性。
- G39　直達車不跑貪婪終點判斷：終點＝申請單目的地，依核准時間累加貨量至容量上限，超出留下一班直達車。
- G40　回程全域直達檢查（所有車適用）：回程路段上存在有效、待處理、時間撞期的直達單→該路段鎖定直達，不收新的非直達貨。
- G41　被鎖定直達的回程車：容量**延續動態淨值**（不切換 3.3 邏輯）、終點仍為出發據點、仍依序經過沿線據點。
- G42　被排擠的非直達單：自動順延下一趟符合條件車次（沿用既有順延機制）。
- G43　回程車經中途據點有貨時：**優先判斷本車剩餘容量**能否順路載，不足才屬多車協調（下階段議題，本期不做）。
- G44　調度室介面須顯示每台車派遣模式（直達／非直達／回程被迫鎖定直達）＋觸發原因。

### 3.4 差旅共乘（模組 C）
- G50　兩種任務型態：來回單（預設，司機車輛全程綁定同批人）、單程單（限交通轉運點）。**不互相混合比對**。
- G51　單程單配對在司機**出發前**完成：同轉運點、回程最早上車時間落在去程送達後 4 小時內→配成一趟；否則純去程。等待時間計入工時。
- G52　司機工時 08:00–20:30（12.5 小時），適用兩型態；預估完成時間（車程＋等待＋緩衝）超過即不可行→標記「待人工協調」。
- G53　媒合觸發＝業務單位**手動按鈕**，批次處理未來 7 天內（以出發日期為準）申請單；已媒合成功的單不重排；失敗的進手動併車。無排程週期、**無保底偵測**（漏按為業務單位責任）。
- G54　自動媒合條件（全部**完全相同**，無時間窗折衷）：出發地、目的地、最早上車時間（去程）／最早回程時間（回程），合併後人數不超容量，且不超工時上限。
- G55　「最晚抵達時間」為系統查車程表算出的參考值，**不參與媒合判斷**。
- G56　手動併車＝向**已確定有車**的單搭便車：候選＝出發日期前後 1 天、已派車的單，**不篩目的地、不比時間**；顯示目的地、出發/最晚抵達時間、申請人姓名與部門/分機（不顯示私人手機）、已載人數/剩餘容量。使用者自行聯繫，按「完成合併」即成立，**不需調度室確認**。
- G57　逾期自動作廢：到出發時間仍未成功→自動作廢、系統通知申請人、紀錄保留供統計、**不轉待人工協調**。
- G58　三種例外機制並存：待人工協調（資源面）／手動併車（需求面）／逾期作廢（併車失敗終局）。
- G59　歸屬據點＝固定行政屬性；**當前位置**才是排班可用性判斷依據。多天任務最後一天回程強制鎖定歸屬據點（仍可正常參與合併）。
- G60　車輛保修：系統內建保修排程功能，業務單位維護，排班自動排除保修期間車輛。
- G61　司機請假：媒合按鈕按下當下即時呼叫內網 API 抓未來 7 天請假資料（精確起訖時間），任務時間與請假時段**重疊即不可指派**。API 故障不特別處理。
- G62　目的地選單制（無地址）；車程表公司自建固定分鐘數，不分尖離峰，系統另加內建緩衝。
- G63　審批流程：員工填單→直屬主管准駁→系統媒合→調度室確認/可直接手動調整（不退回員工）。系統**不做自動通知**，唯逾期作廢例外。

## 4. 執行階段與任務清單

> 每個任務含：產出、驗收條件。Claude Code 完成任務後必須先自行驗證驗收條件再回報。
> 單元測試框架：MSTest 或 NUnit（沿用專案既有者）；核心演算法必須有測試。

### Phase 0　專案骨架與主檔資料

- [ ] **T0-1 資料庫 Schema 初版**
  產出：`db/001_master.sql`。含資料表：
  `VD_Site`（據點，含南北順序欄位）、`VD_Station`（區域內 10 站）、`VD_Building`（站內建物）、
  `VD_TravelTime`（據點→目的地車程分鐘數＋緩衝）、`VD_Vehicle`（含歸屬據點、體積容量、重量上限、資源池別）、
  `VD_Driver`（含歸屬據點、資源池別）、`VD_WasteFactor`（貨物類別浪費係數，含生效狀態）、
  `VD_VehicleMaintenance`（保修排程）、`VD_DayCountDirect` / `VD_DayCountStopover`（天數兩張二維表）、
  `VD_RouteVehicleGroup`（路線-車輛分組）。
  驗收：SQL 可在乾淨資料庫執行無誤；每張表有主鍵與必要索引；附欄位註解。

- [ ] **T0-2 主檔維護頁面（MVC）**
  產出：站點/建物/車程表/浪費係數/保修排程的 CRUD Controller + View。
  驗收：可新增修改停用；係數表修改後快取可手動刷新；保修區間支援單日與日期區間。

- [ ] **T0-3 CLAUDE.md 與專案結構**
  產出：附錄 A 的 CLAUDE.md 落地；solution 內分層：`VD.Core`（演算法類別庫）、`VD.Web`（MVC）、`VD.Tests`。
  驗收：`VD.Core` 不引用 System.Web；全 solution 可建置。

### Phase 1　共用裝載判定引擎（VD.Core）

- [ ] **T1-1 資料模型**
  產出：`CargoItem`（長寬高/類別/數量/重量）、`VehicleCapacity`（可用空間維度/體積/重量上限）、`LoadCheckResult`。
- [ ] **T1-2 WasteFactorProvider**
  產出：static 單例，DB 讀取＋記憶體快取＋保底值＋手動刷新方法。（G03/G04）
  驗收：查無類別回傳保底值不擲例外；快取命中不重複查 DB（測試以計數驗證）。
- [ ] **T1-3 Level 1 + 地板面積瓶頸法**
  產出：體積加總（乘浪費係數）、地板面積瓶頸、長寬比形狀懲罰。（G01/G02）
- [ ] **T1-4 Level 2 單品維度檢查**
  產出：六方向旋轉逐件檢查能否放入車輛可用空間維度。
  驗收：測試涵蓋「體積過但維度不過」「旋轉後才過」等案例。
- [ ] **T1-5 重量累計檢核**
  產出：逐站累計（卸扣收加）加總比較。（G05）
- [ ] **T1-6 整合判定入口**
  產出：`LoadFeasibilityService.Check(...)` 串接 L1→地板面積→L2→重量，回傳含失敗原因碼的結果。
  驗收：所有子檢核失敗原因可區分（供 UI 與稽核顯示）。

### Phase 2　區域內物流排班（模組 A）

- [ ] **T2-1 申請單模型與填單頁**
  一單一目的地、多貨物項目、類別下拉（清單內容留待業務盤點，先做假資料）、收貨時間二選一欄位、上下貨自填時間。（G13/G19）
- [ ] **T2-2 班次與路線引擎**
  固定 10 站順序、無貨跳過、先卸後裝、同站多單時間加總。（G14/G15）
- [ ] **T2-3 媒合迴圈**
  時間軸最近班次→LoadFeasibilityService→裝不下 pass 下一班→當日最後一班終止→同步回傳。（G10/G11/G12）
  驗收：測試涵蓋首班成功／中途成功／全日失敗三情境；全日失敗訊息為「請明天請早再試」且無候補資料寫入。
- [ ] **T2-4 站內時間額度與順延**
  依審核通過時間逐張判定、跳單、自動順延、末班仍不行→即時提醒改期。（G16/G17）
- [ ] **T2-5 收貨時間模式**
  指定期望時間（到站時間差最小，雙向比較）／越快越好（最早可排班次）；兩者皆不影響班次內排序。（G19）
- [ ] **T2-6 兩層審批整合**
  沿用既有主管核准→派車辦公室確認流程；車輛-班次每日人工指派畫面。（G18/G63 物流版）

### Phase 3　駕駛異常回報（模組 A 收尾）

- [ ] **T3-1 回報流程頁**
  回總部後列出本趟站點→標異常站點（不準時/沒出現）→列該站當班申請單→勾選出狀況的單。（G20）
- [ ] **T3-2 存檔與即時寄信**
  記錄到申請單層級；勾選送出即逐單觸發寄信（申請人＋直屬主管，沿用審批對應）。
  驗收：一單一信；正常站點零操作；信件內容含站點/原因/日期（格式為「待後續設計」項，先做簡潔版並標註 TODO）。

### Phase 4　跨據點南北幹線（模組 B）

- [ ] **T4-1 據點順序表與幹線班次模型**
  含直達/非直達勾選欄位、天數對照表查表服務（兩張表）。（G30/G37）
- [ ] **T4-2 非直達貪婪終點判斷**
  沿南北順序逐據點累加，動態淨值容量＋總計時間（行駛＋自報裝卸加總），任一觸頂即終點。（G32/G33/G35）
- [ ] **T4-3 部分裝載**
  整張表單為最小單位、核准時間排序逐張檢查、放不下留下一班。（G34）
- [ ] **T4-4 直達車流程**
  獨立派車、單一目的地、純容量加總、超出留下一班直達車。（G38/G39）
- [ ] **T4-5 回程引擎與全域直達鎖定**
  回程固定回出發據點、反向收送；回程前檢查路段×時間撞期的直達單→鎖定模式；被鎖定車延續動態淨值；被排擠單自動順延；中途據點貨優先由本車剩餘容量吸收。（G36/G40/G41/G42/G43）
  驗收：單元測試覆蓋 3.7 四模式決策矩陣全部五列情境。
- [ ] **T4-6 調度室模式顯示**
  每台車顯示派遣模式與觸發原因。（G44）

### Phase 5　差旅共乘自動媒合（模組 C）

- [ ] **T5-1 申請單與審批**
