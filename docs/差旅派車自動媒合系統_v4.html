00本版更新摘要

  • 語意澄清（非新決策）：「歸屬據點」是車輛/司機固定的行政屬性；「當前位置」才是排班演算法實際判斷可用性的依據。多數時候兩者相同，僅多天任務進行中會暫時不一致。
  • 新增車輛保修檢核：系統內建保修排程功能，由業務單位維護，排班時自動排除保修期間的車輛。
  • 新增司機請假檢核（API串接）：即時串接公司既有休請假系統，於媒合觸發當下抓取未來7天內司機請假資料（精確起訖時間），任務時間與請假時段重疊即不可指派。API故障情境不特別處理。
  • 車次成立條件更新：新增「不在保修期間」「與請假時段無重疊」兩項檢核。

01系統定位

核心問題

多組獨立提出的出差需求，能否合併共乘同一台車——屬於派工型的延伸版（出差共乘媒合），非叫車／載客平台。公司在全台約 8 個據點，各據點皆有員工與數台車輛。

02任務型態：來回單與單程單

系統處理兩種性質不同的任務型態，媒合與資源綁定邏輯各自獨立，不互相混合比對。

來回單（預設型態）

定案內容

司機／車輛全程綁定同一批人，去程送達後在當地待命，回程載回原班人馬。去程與回程視為同一趟任務的兩端，不各自獨立找其他需求合併。單日或多日任務皆適用此邏輯。

單程單（新增型態）

定案內容

專指送往／來自港口、機場、高鐵站等交通轉運點的單程需求。系統須在司機出發前就完成配對：搜尋同一轉運點、回程最早上車時間落在去程送達後 4 小時內的回程單程單，配成一趟完整行程一併指派。若 4 小時內無可配對回程單，則排為純去程單程單，司機送達後直接返回出發地或接下個任務。單程單只能跟單程單配對，不會跟來回單混合比對。

此為配對階段（出發前）就決定的結果，非司機出發後臨時在原地等待的即時判斷。

03司機工時限制

定案內容

司機表訂工時 08:00–20:30，上限 12.5 小時。此限制同時適用來回單與單程單：

  • 來回單：回程送達出發地時間不得晚於 20:30
  • 單程單：無論是否配對到回程，司機最後完成任務（含等待配對）的時間不得晚於 20:30；等待配對的時間計入司機工時佔用，非空閒時間

排班演算法新增檢查項：預估完成時間（含車程＋等待＋緩衝）是否超過 20:30。超過即判定該指派不可行，標記「待人工協調」，不強行派車讓司機超時。

03B媒合觸發機制

定案內容

自動媒合不是即時觸發，而是由業務單位手動按下按鈕才會執行一次批次媒合。

  • 每次觸發，處理範圍是按下當下起算未來 7 天內、以出發日期為準的申請單
  • 已經媒合成功的單不會被重新異動（不會被下一次觸發打散重排）
  • 媒合失敗的單，才會進入手動併車模式
  • 觸發頻率不固定：業務單位想到就按，沒有排程週期
  • 系統不做保底偵測：若長時間未按導致某張單的出發日期從未落入任何一次的 7 天範圍內，該單即不會被自動媒合處理到——此為業務單位操作責任，系統不主動補救

技術影響：資料庫需記錄每次媒合批次的觸發時間戳記，以及每筆申請單「是否已被某次批次處理過、結果為何」；演算法主流程起點由「需求送入即時處理」改為「業務單位觸發時，批次撈取範圍內待處理單一次跑完」。

04申請表單時間欄位

欄位說明性質
最早上車時間使用者最早可被載走的時間（去程）使用者填寫，媒合判斷依據
最早回程時間使用者最早可上車回程的時間使用者填寫，媒合判斷依據
最晚抵達時間系統依車程表算出的預計抵達時間系統算出的參考資訊，不參與媒合判斷

05自動媒合條件

  • 出發地完全相同
  • 目的地完全相同
  • 最早上車時間完全相同（去程）／最早回程時間完全相同（回程）
  • 合併後總人數未超過車輛容量
  • 指派後預估完成時間未超過司機工時上限（20:30）

不存在「時間窗重疊、系統挑折衷值」的邏輯——時間欄位必須完全一致才能自動合併。

06手動併車模式（完整重寫）

當自動媒合完全失敗（找不到任何可合併對象）時，該申請單進入手動併車模式。本輪對此機制做了根本性修正——從「同樣待配對者互相配對」改為「向已確定有車者搭便車」。

候選清單範圍與顯示欄位

定案內容

候選對象：出發日期在申請日前後1天內、已確定有派車的其他申請單（不篩選目的地——不論候選單去哪裡，只要日期範圍符合、已有車，都列入清單，由使用者自行判斷是否順路）。

顯示欄位：目的地、出發時間／最晚抵達時間、申請人姓名與部門/分機（不顯示私人手機）、該車輛已載人數/剩餘容量。

操作與完成機制

定案內容

使用者自行從候選清單聯繫對象：

  • 對方同意 → 使用者按下「完成合併」，即視為已媒合成功，不需調度室額外確認
  • 對方拒絕 → 回到候選清單，可繼續嘗試聯繫其他候選對象

逾期自動作廢機制

定案內容

若一直等到申請的出發時間點仍未媒合成功，該筆申請單自動作廢：

  • 系統通知申請人：用車未能媒合成功、已自動作廢
  • 作廢紀錄保留（供後續統計媒合失敗率，作為檢討演算法或評估資源是否足夠的依據）
  • 不轉「待人工協調」——作廢即為最終結局，後續由申請人自行決定（改搭其他交通方式或另行聯繫調度室）

07核心合併邏輯（通用原則）

終點判斷的通用性

「終點相同即可合併」是來回單媒合的通用邏輯，不分去程回程、不分是否為多天任務的最後一天。多天任務最後一天的回程終點會被鎖定為歸屬據點，但同樣正常參與合併比對。

優化目標優先順序

管理階層明確要求「盡量不要有空車移動」，此為最優先目標，其次才是減少車次總數。

排班模式與演算法選型

目前朝全自動生成研討，但保留必要時人工介入的空間。MVP 採用貪婪規則引擎，主流程依任務型態（來回單／單程單）分兩條分支處理。

08目的地與車程資料

目的地資料

沒有地址，只有目的地名稱；系統開發網頁表單，目的地採選單制（非自由文字輸入）。

車程時間表

公司自行建置常用目的地清單與「據點→目的地」車程時間對照表，不串接外部地圖 API。數值為固定分鐘數，不分尖峰離峰；系統另外內建緩衝時間。

09車輛與司機資源模型

歸屬據點 vs 當前位置（語意澄清）

定案內容

歸屬據點：車輛/司機在行政與資產管理上固定隸屬的據點（保養、常駐、鑰匙管理皆在此），這個屬性不會因單次出差而改變。

當前位置：車輛/司機在某個時間點實際所在的地理位置，排班演算法判斷「今天這台車/這位司機能不能被指派」時，看的是當前位置，不是歸屬據點。

兩者關係：沒有進行中的多天任務時，當前位置＝歸屬據點。多天任務進行中，當前位置會暫時偏離歸屬據點；任務最後一天的回程被強制設定回歸屬據點，結束後兩者重新一致。

多天任務（來回單）

任務最後一天的回程終點強制鎖定為歸屬據點；該回程仍正常參與合併比對，只要合併對象終點同樣是這個歸屬據點即可。

司機：獨立資源

司機為獨立管理的資源類型，與車輛分開建模。

車輛保修檢核（新增）

定案內容

系統內建保修排程功能，由業務單位手動維護——登記某台車在某個日期區間（或單日）進廠保修、不可派車。排班時直接將保修期間的車輛排除於可用清單之外。

司機請假檢核（新增，API 串接）

定案內容

司機休請假資料透過 API 即時串接公司既有的休請假系統，於「媒合觸發按鈕」按下當下，即時呼叫 API 抓取該次範圍（未來7天）內所有司機的請假資料。

請假資料為精確起訖時間（例如09:00–13:00），非簡單的上午/下午分類。排班判斷邏輯：任務的預估時間範圍只要與請假時段有重疊，該司機當天此任務即不可指派；若任務完全落在請假時段外，仍可正常指派。

API 故障情境不列入考量，不特別設計失敗處理機制。

車次成立條件（更新版）

一個車次要成立，需同時滿足：

  • 車輛可用（當前位置對、時段無衝突、不在保修期間）
  • 司機可用（當前位置對、時段無衝突、與請假時段無重疊）
  • 目的地車程資料存在
  • 預估完成時間未超過司機工時上限（20:30）

13問答逐條紀錄

Q1　這個系統要解決的核心問題是什麼？
多組獨立提出的出差需求能否合併共乘同一台車——屬於派工型延伸（出差共乘媒合），非叫車平台。
Q2　判斷「兩組出差需求可以合併」的規則是什麼？
先做「同起點、同終點、時間窗重疊」的簡單合併邏輯（後於Q21/Q22/Q26修正為完全相同）。
Q3　時間不同的兩組如何處理回程？
去程和回程視為兩筆獨立的派車需求（此規則後於Q34限定為僅適用單程單，來回單去回程綁定同一資源）。
Q4　「合併省車次」與「減少空車移動」目標衝突時如何取捨？
長官需求是「盡量不要有空車移動」，這是最優先目標。
Q5　系統預期是「輔助建議工具」還是「全自動生成」？
目前朝自動生成研討，但必要時可讓人工介入。
Q6　自動生成要用什麼等級的演算法邏輯？
先用簡單規則引擎（貪婪法）看看。
Q7　出差需求資料從哪裡來、包含哪些欄位？
沒有目的地地址，只有目的地名稱；要開發網頁表單。
Q8　目的地要怎麼變成系統可比對、可算車程的資料？
常用目的地清單與據點到目的地車程時間，公司自建，不串 Google Maps API。
Q9　車程時間表怎麼建、精細度到多少？
採用建議預設值：固定數字、不分尖峰離峰、系統內建緩衝時間。
Q10　車輛是否只能給該據點使用，還是可跨據點調度？
車輛屬於某據點，但可能因出差到新地點，隔天從該地當出發地。
Q11　車輛當前位置怎麼更新、在外地的車能否被下一需求使用？
司機出發前已被告知單日或多天任務；不論天數，任務最後一天一定要回到所屬地。
Q12　司機是否為獨立於出差人員的專職角色？
司機是獨立資源，同意。
Q13　需求排不進去時系統要如何呈現、誰處理？
標記「待人工協調」，顯示原因，提供人工手動指派工具。
Q14　申請流程是否需要主管簽核？
員工申請時直屬主管審一次，調度室只是做確認。
Q15　主管駁回的申請如何處理？調度室發現排錯要退回還是手動改？
保留紀錄但不進排班池；調度室直接手動調整，不退回員工。
Q16　系統要不要自動通知司機/員工排班結果？
由調度室告知就可以了，系統不做自動通知（後於本輪新增：逾期作廢例外會系統通知）。
Q17　表單時間欄位如何設計？
使用者要填「預期出發時間」，加上「最晚抵達時間」「回程時間」（後於Q25/Q26整個改寫）。
Q18　預期出發時間效力（已作廢）
因時間欄位模型重新定義，此題不再適用。
Q19　多天任務最後一天的回程，是否完全不能合併？
可以合併載其他人，只是回程目的地必須是同一個歸屬據點。
Q20　非最後一天的回程，終點判斷邏輯是否不同？
邏輯完全一致，都用「終點相同」的通用規則判斷合併。
Q21　自動媒合的時間比對，是「完全相同」還是「容許誤差」？
完全相同。
Q22　自動媒合完整條件重新定義（已由Q26取代）
初版誤將比對基準定為「最晚抵達時間」，後修正為「最早上車時間／最早回程時間」。
Q23　手動併車模式候選比對基準（已由Q39/Q40取代）
初版採「同樣待配對者互相配對＋時間窗」，後整個改為「向已有車者搭便車＋前後1天不比對時間」。
Q24　手動併車模式完整候選條件（已由Q39/Q40取代）
同Q23，機制已整個重寫。
Q25　表單時間欄位重新定義為「最早上車時間」「最早回程時間」，如何對應原本概念？
最早上車時間＝預期出發時間；最早回程時間＝結束時間；最晚抵達時間變成系統查表算出的參考數字。
Q26　自動媒合比對基準是否改回「最早上車時間完全相同」？
同意修正：媒合條件為出發地／目的地／最早上車時間（或最早回程時間）完全相同，人數未超容量。
Q27　手動併車模式由誰聯繫？
由使用者自行聯繫。
Q28　手動併車候選清單要顯示哪些資訊？
顯示姓名、部門/分機、目的地、時間、人數，不顯示私人手機。
Q29　合併結果如何寫回系統（已由本輪定案取代）
原列為待業務確認，本輪定案：使用者按下「完成合併」即成立，不需調度室確認。
Q30　候選清單時間範圍上限（已由Q40取代）
原列為待業務確認，本輪定案：前後1天。
Q31　搭便車對象拒絕後如何處理？
回候選清單，可繼續嘗試聯繫其他候選對象。
Q32　手動併車模式有沒有時間期限／保底機制？
等到出發時間仍未媒合成功則自動作廢，通知申請人並保留紀錄，不轉待人工協調。
Q33　候選比對邏輯：兩兩比對vs群組比對（已作廢）
因時間窗機制已取消（改為前後1天、不比對時間），此題不再適用。
Q34　司機/車輛與出差人員的綁定關係為何？
來回單：司機全程陪同同一批人，載出跟載回；單天當天回到出發地，多天全程陪同。
Q35　單程單的等待與返程機制？
送達交通轉運點後，預設可等待4小時，若有其他單程單從該轉運點回司機出發地，即可配對成立；單程單只能加單程單。
Q36　配對是即時發生還是出發前決定？
司機出發前就要知道今天的任務是否要等待，配對必須在出發前完成，非即時動態判斷。
Q37　司機工時上限如何套用在演算法判斷？
12.5小時（08:00–20:30），適用來回單與單程單，等待時間計入工時，超時即判定不可行、轉待人工協調。
Q38　是否還有第三種任務型態？
目前沒有收到新的需求，只有來回單與單程單兩種。
Q39　手動併車候選對象是「同樣沒車的人」還是「已有車的人」？
修改為一定要搭上已確定有車的單。
Q40　候選清單要不要篩選目的地？
不篩選目的地，前後一日所有已確定有派車的單都列出來。
Q41　候選清單要顯示哪些欄位？
目的地、出發時間/最晚抵達時間、申請人姓名與部門/分機、車輛已載人數/剩餘容量。
Q42　申請單逾期作廢後，系統要不要通知或保留紀錄？
作廢時要通知申請人，也保留紀錄，不需要轉人工協調。
Q43　媒合觸發的範圍與規則？
按下按鈕後7天內的單參與媒合；已媒合成功的單不會再異動；媒合失敗才進入手動二次媒合。
Q44　按鈕預期多久按一次？
業務單位想到就來一次，非固定排程。
Q45　若業務單位長時間未按導致單過期未被處理，系統要不要保底偵測？
業務單位漏了就漏了，那是業務單位要負責的事，系統不做保底防範。
Q46　車輛的「歸屬據點」與「當前位置」是否矛盾？
不矛盾：歸屬據點是固定行政屬性，當前位置才是排班判斷依據，多數時候兩者相同，僅多天任務進行中會暫時不一致。
Q47　車輛保修與司機請假這兩種不可用狀態，資料怎麼來？
車輛保修在本系統內建功能供業務單位維護；司機休請假用API方式串聯既有休請假系統。
Q48　司機請假API同步頻率與故障處理？
司機請假的顆粒度本來就可以排到半天；休請假系統若故障不列入考量。
Q49　半天請假如何定義比對？
休請假系統會回傳精確的起訖時間（如09:00-13:00），排班用時間重疊比對即可，不需另定義半天切分點。

14名詞對照表

來回單
司機/車輛全程綁定同一批人，去程送達後待命，回程載回原班人馬，去回視為同一趟任務
單程單
送往/來自交通轉運點的單程需求，出發前完成配對，4小時時間窗內可配對回程單程單，只能單程配單程
司機工時上限
08:00–20:30，共12.5小時，適用兩種任務型態，超時判定指派不可行
最早上車時間
去程使用者最早可被載走的時間，是自動媒合的判斷依據之一
最早回程時間
回程使用者最早可上車的時間，是自動媒合的判斷依據之一
最晚抵達時間
系統依車程表算出的預計抵達時間，僅供參考顯示，不參與媒合判斷
自動媒合
出發地、目的地、最早上車/回程時間皆完全相同，人數未超容量，且不超工時上限時，系統自動合併為同一車次
手動併車模式
自動媒合失敗後，系統列出前後1天已確定有車的候選單，由申請人自行聯繫搭便車
逾期自動作廢
手動併車模式到出發時間仍未媒合成功，系統自動作廢申請單，通知申請人並保留紀錄
待人工協調
因資源面問題（無可用車/司機/車程資料/超工時）無法自動排班的狀態，交由調度室處理
歸屬據點
車輛/司機行政與資產管理上固定隸屬的據點，不因單次出差改變
當前位置
車輛/司機實際所在地理位置，是排班演算法判斷可用性的依據，非歸屬據點
保修排程
系統內建功能，業務單位登記車輛保修期間，排班時自動排除
請假檢核
API即時串接休請假系統，抓取司機精確請假起訖時間，與任務時間重疊即不可指派
車輛當前位置
車輛動態追蹤的實際所在地，非固定的歸屬據點
多天任務
來回單任務標記天數，最後一天回程終點強制設為歸屬據點，但仍可正常參與合併
人工覆寫
調度室手動指派、修改系統自動排班結果的紀錄標記
