# 路程／時數資料規格與測試資料產生規則

> **本檔不含任何實際資料。** 業務單位提供之實際院區名稱、路程時數、最短天數表與行程
> 範例，一律**不進入本 repo**（本 repo 會自動部署至公開 GitHub Pages）。實際資料由業務
> 單位於 repo 外自行保管，導入時依第 6 節程序覆寫。
>
> 本檔記錄的是**結構與規則**：資料長什麼形狀、程式如何取用、以及目前用來替代的虛構
> 測試資料是怎麼產生的。

---

## 1. 核心公式

```
每日在勤上限 ≥ 待勤 + 緩衝 + 裝貨 + 開車 + 卸貨 + 休息 + 緩衝
```

| 項目 | 定義 | 程式對應 |
|---|---|---|
| 每日在勤上限 | 單日在勤時數天花板 | `DB.dailyDutyMin` |
| 待勤 | 上班至出勤 | 併入 `DB.prepMin` |
| 緩衝（前） | 車輛檢查及前往報到地點 | `DB.prepMin` |
| 裝貨／卸貨 | 物品裝卸時間（**由申請單位自填**） | 單上 `loadMin` / `unloadMin` |
| 開車 | 出發地至目的地車程 | `ModuleB.travelMin()` 查表 |
| 休息 | 連續駕駛之休息與用餐 | `DB.driverBreaks` |
| 緩衝（後） | 任務完成後車輛檢整＋返回休息地 | `DB.closeMin` ＋ `returnToRestMin()` |

## 2. 限制條件（三項）

實際條文含受限地區名稱，此處以**參數與旗標**表述，地區身分由主檔資料決定。

| # | 條件 | 程式對應 |
|---|---|---|
| 1 | 出車前 N 日之指定時刻停止媒合 | `DB.matchCutoffDaysBefore` ／ `DB.matchCutoffTime` ／ `ModuleB.meetsCutoff()` |
| 2 | 每日指定時刻後不前往受限據點 | `DB.noArrivalAfter` ＋ 據點旗標 `lateRestricted` ／ `ModuleB.lateArrivalBlocked()` |
| 3 | 受限據點之回程媒合，裝貨須於指定時刻前完成 | 據點旗標 `returnLoadBy` ／ `ModuleB.returnLoadDeadlineOk()` |

要把某據點列為受限地區，在 `DB.sites` 該筆加上：

```js
{ id: 'Dx', ..., lateRestricted: true, returnLoadBy: '14:00' }
```

不需改任何演算法。目前測試資料以最南端據點 `D1` 代表一個受限據點。

## 3. 路程表結構

實表為**單一矩陣同時承載兩種車型**：對角線右上＝大車、左下＝小車，同車型內視為對稱。
程式端展開為兩張獨立查表：

```js
DB.siteTravel = {
  big:   { 'D1|D2': 30, ... },   // 分鐘
  small: { 'D1|D2': 30, ... },
}
```

取用一律經 `ModuleB.travelMin(fromId, toId, sizeClass)`，同車型內自動反向查詢。
商務車（模組 C）無大小車之分，固定取 `small`。

實表已知特徵（測試資料據此產生）：

1. **最小計算單位 30 分鐘**，所有格皆為 0.5 小時的整數倍。
2. **僅含路程時間**，不含裝卸、休息、用餐。
3. **次可加性**：長程直達時間 < 沿途各段相加（走高速公路的效果）。
4. **大車固定較小車多 0.5 小時**；小車本身僅 0.5 小時之短程則兩者相同。

## 4. 測試資料產生規則（目前 repo 內的值）

`js/data.js` 不寫死 169 格，而是由南北主軸位置展開，保留上述四項特徵：

```js
siteTravelPos:   { D1: 0, D2: 0.5, ..., D10: 6.7 }  // 各節點位置（小時，南→北遞增）
travelUnitMin:   30      // 最小計算單位
travelConcavity: 0.04    // 次可加性：每小時折減 4%，折減上限對應 5 小時
bigExtraMin:     30      // 大車加成
```

展開式（`buildSiteTravel`）：

```
raw   = |pos[a] − pos[b]|                              // naive 相加距離（小時）
adj   = raw × (1 − travelConcavity × min(raw, 5))      // 次可加性折減
small = max(travelUnitMin, round_to_unit(adj × 60))    // 相異節點至少一個計算單位
big   = small ≤ travelUnitMin ? small : small + bigExtraMin
```

產生結果抽樣（分鐘）：

| 路段 | 小車 | 大車 |
|---|---|---|
| D9→D8（相鄰短程） | 30 | 30 |
| D8→D7 | 60 | 90 |
| D1→D6（南→中） | 180 | 210 |
| D6→D10（中→北） | 180 | 210 |
| **D1→D10（南→北直達）** | **330** | **360** |

D1→D6 ＋ D6→D10 ＝ 360 分 > 直達 330 分，次可加性成立。

休息會館同樣以位置參數產生（南／中／北各一），`returnToRestMin()` 取最近者。

**這些數值全為虛構**，僅用於讓演算法在合理量級下被測試；不代表任何實際路線。

## 5. 其他表格的處理方式

| 表格 | 目前狀態 |
|---|---|
| 休息／用餐門檻 | 規則已實作於 `DB.driverBreaks`（依純累積行駛時間觸發，五門檻共用時數線、每日歸零）；不另存表格副本 |
| 出差最短天數表 | `DB.minTripDays` 保留結構（車型 × 目的地），**僅供排班參考、不參與運算**；目前為虛構值 |
| 行程驗算範例 | 不留存；驗算邏輯已由 `newDutyClock()` 與測試涵蓋 |

## 6. 導入實際資料的程序

1. 取得實表後，**不要 commit 進本 repo**（公開部署）。
2. 以真實矩陣直接覆寫 `DB.siteTravel.big` / `DB.siteTravel.small` 兩個物件即可；
   `siteTravelPos` / `travelConcavity` / `bigExtraMin` 屆時可整組刪除。
3. 受限據點於 `DB.sites` 補 `lateRestricted` / `returnLoadBy` 兩個旗標。
4. `DB.minTripDays` 補實際天數（不影響運算，僅顯示參考）。
5. 演算法、模組介面與測試皆不需修改——結構已與實表對齊。

若正式環境需要保留實際資料，建議走**設定檔外掛**：於 `js/` 外提供一支不納版控的
`config.local.js`，載入後覆寫上述物件，並將該檔加入 `.gitignore`。
