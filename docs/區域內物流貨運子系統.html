01 貨物裝載判定演算法

1.1 問題背景

貨物裝載媒合的本質是 3D Bin Packing 問題，屬於 NP-hard 問題，不存在多項式時間的最優解， 必須採用啟發式或近似解法。系統需求是「快速媒合」，因此放棄真實的 3D 空間碰撞模擬， 改以分層快篩取代：Level 1 體積篩選 + Level 2 單品維度檢查。

1.2 三層準確度模型

LEVEL 1
體積加總

最快、最不準。將所有貨物體積加總，與車輛容量比較，僅為必要條件之一，無法反映實際堆疊可行性。

LEVEL 2
單品維度檢查

逐件檢查貨物長寬高（含六方向旋轉）是否能放入車輛可用空間維度，屬於必要條件，仍非充分條件。

LEVEL 3
真實空間排列模擬

唯一準確的方法，需完整碰撞檢測與空間排列演算法，計算成本高，不符合快速媒合需求，本系統不採用。

決策
系統僅採用 Level 1 + Level 2，不做 Level 3 真實碰撞檢測。
在「快速媒合」的核心需求下，Level 3 的運算成本不符效益；Level 1+2 已能提供足夠可用的必要條件判斷，且邏輯透明、易於人工覆核。

1.3 中間強化方案：地板面積瓶頸法

決策
在不做碰撞檢測的前提下，為求「最保險」，以地板面積瓶頸法與長寬比形狀懲罰係數取代單純體積加總， 降低因形狀不規則造成的誤判風險。
純體積加總容易高估可裝載量（例如細長物品實際佔用地板面積遠大於其體積比例），地板面積與形狀懲罰能在不做碰撞模擬的情況下，提供更保守、更貼近實際的估算。

1.4 浪費係數與貨物類別

決策
由於貨物形狀不規則、缺乏精確形狀資料，改以「貨物類別」對應「浪費係數」的方式修正有效體積。 使用者填單時透過類別下拉選單額外勾選，對應後端係數表計算有效體積。
使用者填單通常只會填長寬高，無法期待其提供精確形狀資訊；以類別粗略估算浪費空間，是精確度與填單便利性之間的合理折衷。

1.5 係數表設計

決策
浪費係數表設計為可動態調整：資料存於資料庫，程式端以記憶體快取讀取，並含保底值機制（查無對應類別時使用預設係數，不中斷流程）。 係數 Provider 採 static 單例（不使用依賴注入 DI），內部自行讀取設定檔取得資料庫連線字串。
係數需要業務單位隨時可調整，不應寫死在程式碼；static 單例設計符合系統既有 MVC / .NET Framework 4.8 的架構慣例，不需引入額外的 DI 容器。

1.6 程式碼設計（C#）

報告第一版已包含完整 C# 程式碼章節，涵蓋以下模組：

02 端到端排班架構

2.1 架構範圍

端到端流程為：填單 → 媒合最近一台車 → 裝得下就上車、裝不下 pass 到下一台。 本部分確認「最近」的定義、同步/非同步前提，並設計整體端到端架構（非僅後端）。

2.2 關鍵定義

決策
「最近的一台車」定義為時間軸最近的下一班次，不論空間距離。
決策
媒合結果為同步等待結果，非非同步通知。
決策
本次設計範圍為整體端到端架構，非僅聚焦後端。

2.3 併發與技術前提

決策
因載運量不高，不需考慮併發扣容量（多人同時搶同一班次容量）問題，Repository 採單純 讀取／判斷／寫入即可，不需額外的鎖定或交易隔離機制。
決策
系統為 MVC、.NET Framework 4.8，不需要獨立 API 層。媒合迴圈可找到「當日最後一班」， 因此移除固定 maxAttempts 上限，迴圈終止條件改為「當日最後一班仍裝不下」。
決策
若找到當日最後一班仍裝不下，不留候補紀錄，直接提示使用者「請明天請早再試」， 不寫候補、不排入隔日。
維持系統「不做靜默失敗」的設計原則，同時避免候補佇列帶來的額外狀態管理複雜度。

2.4 媒合流程圖

申請單提交 │ ▼ 找時間軸最近的下一班次 │ ▼ Level 1 + Level 2 + 係數修正 → 裝得下？ │ ├─ 是 → 排入該班次（同步回傳結果） │ └─ 否 → pass 到下一班次 │ ▼ 是否為當日最後一班？ │ ┌─────────┴─────────┐ ▼ ▼ 否，繼續找下一班 是，仍裝不下 │ 提示使用者「請明天請早再試」 （不留候補、不排入隔日）

03 物流子系統整體架構

3.1 系統定位與資源

決策
物流貨運為派遣系統下獨立於商務用車共乘的子區塊，車輛/司機資源池分開，兩邊互不搶用。
貨運通常需特定車型（貨車、噸位限制），與商務用車在車輛屬性上差異大，混用會使可用性判斷複雜化。
決策
沿用原系統兩層審批流程：部門主管核准 → 派車辦公室確認排程（物流走員工申請制，非訂單自動觸發）。

3.2 申請單結構

決策
一張申請單 = 一個目的地，可填多筆貨物項目（品項/長寬高/類別/數量）。多站點巡迴由「固定路線」機制處理，不靠單張申請單串多站。
決策
貨物類別沿用「下拉選單 + 後端浪費係數表」機制，但類別清單內容需依物流實際貨物型態重新盤點，不可直接套用舊有範例類別。

3.3 目的地與路線設計

決策
目的地透過兩層階層選單呈現：先選區塊（站點），再選區塊內具體建築物，最終仍對應單一目的地。
決策
路線為固定 10 站，站點清單、站點對應的建築物清單皆為人工維護的主檔資料（比照目的地主檔），不做動態路線生成。
決策
車輛依固定地理順序逐站停靠，沒貨物需求的站點跳過，有貨站點之間不重新排序（無動態最短路徑）。

3.4 送收貨與站內處理

決策
同一趟路線允許送貨與收貨混合，同一站點可能同時發生兩者；站內固定順序為先卸貨（釋放容量）→ 再裝貨（佔用容量）。
決策
上下貨時間由申請人自行填寫；同站多張申請單的上下貨時間以加總方式計入該站總停留時間。

3.5 容量判定

決策
沿用 Level 1（體積加總）+ Level 2（單品維度）+ 類別浪費係數，新增重量維度：車輛設定「總重量上限」，逐站累計（卸貨扣、收貨加），採加總比較，不做單品層級重量檢查。

3.6 站內時間額度與跳過規則

決策
同站點多張申請單依審核通過時間排序，逐張判斷該站剩餘時間額度是否容納得下，額度用完的較晚申請單被跳過（以申請單為單位，非整站）。
決策
時間額度不足被跳過的申請單，自動順延到下一個經過同站點的班次，不需人工重新申請；若嘗試到當天最後一班仍排不進去，系統即時跳提醒，請使用者自行修改申請日期。
與商務用車共乘子系統不同，此處不進入人工協調候補，因為排擠是系統邏輯判斷的結果，視為「順延下一班」較合理。

3.7 車輛指派模式

決策
路線與車輛為分組對應（例如路線 A 固定由車 1/2/3 等執行）。但「今日哪台車跑哪個班次」為人工每日手動排定，系統僅記錄班次-車輛對應關係，並代入該車的容量/重量上限參數。
車輛日常調度常牽涉維修保養、司機請假等現實因素，交由人工決定較有彈性；系統自動排的價值相對有限。

3.8 區域內物流路線示意

起點站 │ 固定地理順序 → 逐站檢查是否有貨物需求 ├─ 站點 1：無貨需求 → 跳過 ├─ 站點 2：先卸貨（釋放容量）→ 再裝貨（佔用容量） │ 時間額度：依審核通過時間逐張申請單判斷 ├─ … └─ 站點 10 │ ▼ 容量判定：Level 1 體積 + Level 2 維度 + 類別係數 + 總重量上限

04 收貨時間與駕駛異常回報

4.1 收貨時間欄位設計

決策
收貨時間欄位為二選一：「指定期望時間」或「越快越好」，不可兩者並存。
決策
指定期望時間：僅影響「選班次」，系統找當天經過該站點、到站時間與期望時間差最小的班次 （提早、延後兩方向都嘗試比較）。越快越好：直接找當天最早排得進去的班次。
將「挑選班次」與「班次內搶時間額度」責任分開，避免期望時間與審核時間互相覆蓋。
決策
不論哪種模式，排入班次後，同站點內申請單處理順序一律仍依審核通過時間排序，兩種模式皆不享插隊優先權。
決策
若最接近/最早的班次也塞不下，沿用既有機制：自動順延下一班 → 當天排不進去則提醒使用者改期。

4.2 收貨時間排班流程

申請單提交（收貨時間：指定時間 / 越快越好） │ ├─ 指定期望時間 → 找到站時間與期望時間差最小的班次 │ └─ 越快越好 → 找最早排得進去的班次 │ ▼ 該班次內依「審核通過時間」排序判斷時間額度 │ ┌─────────┴─────────┐ ▼ ▼ 額度足夠 → 排入 額度不足 → 順延下一班 │ 當天最後一班仍不足 → 提醒使用者改期

4.3 駕駛異常回報機制

決策
駕駛跑完整趟路線、回到總部後才回報，且只需標記異常站點（不準時／沒出現），正常站點免確認。
決策
回報須記錄到申請單層級（而非只到站點層級），因同站點同班次可能有多張不同申請人的申請單。
決策
異常記錄用途為存檔備查 + 立即自動寄信通知，不做「顯示於申請畫面」的功能設計（此方向已被自動通知取代）。
決策
駕駛回報異常後立即觸發（非批次彙整）自動寄信，通知對象為該申請單的申請人本人＋其直屬主管， 單張申請單對應單封信，收件人沿用審批流程既有的「申請人 → 直屬主管」對應關係，不另建資料表。

4.4 駕駛異常回報流程

駕駛完成整趟路線 → 回到總部 │ ▼ 系統列出本趟站點清單 │ └─ 異常站點 → 標記原因（不準時 / 沒出現） │ ▼ 列出該站當班次對應申請單清單 │ ▼ 駕駛勾選是哪張（或哪幾張）申請單出狀況 │ ┌─────────┴─────────┐ ▼ ▼ 存檔備查 立即自動寄信（申請人 + 直屬主管）

05 名詞定義總表

Level 1（體積加總）
將貨物體積加總與車輛容量比較，判定裝載可行性的最快、最不準方法，僅為必要條件。
Level 2（單品維度檢查）
逐件檢查貨物長寬高（含六方向旋轉）能否放入車輛可用空間維度，屬必要條件。
Level 3（真實空間排列模擬）
唯一準確的裝載判定方法，需完整碰撞檢測，運算成本高，本系統不採用。
浪費係數
依貨物類別修正有效體積的係數，用於彌補缺乏精確形狀資料時的裝載判定誤差。
係數 Provider
以 static 單例實作的浪費係數讀取機制，含記憶體快取與保底值，內部自行讀取設定檔連線字串，不使用依賴注入。
時間軸最近班次
媒合演算法中「最近的一台車」的定義，指時間軸上最近的下一班次，不考慮空間距離。
物流貨運子系統
派遣系統下獨立於商務用車共乘的子區塊，擁有獨立車輛/司機資源池。
站點/區塊
固定 10 站路線中的一站，每站對應一個地理區塊，區塊內含多棟可選建築物。
目的地階層選單
使用者填單時先選區塊（站點），再選區塊內具體建築物，最終仍對應單一目的地。
站內處理順序
同一站點固定「先卸貨（釋放容量）→ 再裝貨（佔用容量）」。
車輛總重量上限
車輛容量限制的第二維度，與體積（Level 1+2）並列，逐站累計加總比較。
期望收貨時間
申請人在填單時指定的期望收貨時間點，用於影響系統選擇該申請單應排入哪一個班次。
越快越好模式
收貨時間欄位的另一種選項（與「指定期望時間」二選一），代表不指定確切時間，系統直接嘗試安排最早可行班次。
駕駛異常回報
駕駛完成整趟路線、回到總部後，針對本趟路線中「使用者不準時」或「使用者沒出現」的站點所做的回報，記錄到申請單層級。
