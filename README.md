# 車輛派遣系統整合 — 互動原型 v0.2

依 [`docs/PLAN.md`](docs/PLAN.md) 建置的**第一階段可動版雛形**。
純 HTML + JavaScript，**無資料庫、無後端、非 .NET Framework**，可直接於瀏覽器開啟操作，
用於驗證三模組的核心業務邏輯（Guardrails G01–G63）與端到端流程。

## 架構：申請端與審核端分離（共 6 個業務單元）

依審批流程（G63），「使用者申請」與「業務單位審核/調度」拆為**獨立單元**。
三個模組各拆成兩個軟體單元，共 **6 個業務單元**（另加 2 個共用基礎單元）：

| 模組 | 申請端（使用者） | 審核/調度端（業務單位） |
|---|---|---|
| A 區域內物流 | 收貨申請、查看狀態 | 主管准駁 → 執行媒合 → 路線班次、駕駛異常回報 |
| B 南北幹線 | 幹線託運申請、查看狀態 | 主管准駁 → 貪婪/直達派車決策、模式顯示 |
| C 差旅共乘 | 出差用車申請、查看狀態 | 主管准駁 → 批次媒合、資源檢核、手動併車、逾期作廢 |

單據流轉（含接受/交貨確認）：

- **A 物流**：`待審核 → 核准 → 已排班 → 接收人接受 → 交貨確認`
- **B 幹線**：`待審核 → 核准 → 已派車 → 接收人接受 → 交貨確認`
- **C 共乘**：`待審核 → 核准 → 已媒合 → 乘客確認上車 → 行程完成`

接受由申請/接收端操作、交貨（或完成）可由接收端或調度端確認；
審核端各有一個追蹤一覽（已排定車次 / 已派車貨況 / 派車追蹤）顯示車輛、
班次或司機、以及接受與交貨/完成狀態。駁回保留紀錄但不進排班池。

## 申請端畫面：查詢 → 列表 → 新增 / 明細

三個模組的申請端（A 收貨申請、B 幹線託運申請、C 出差用車申請）採企業常見的
主檔查詢頁樣式：

1. 點入後先出現**查詢畫面**：上半查詢條件、右上角「查詢 / 新增」兩顆按鈕
2. 下半是**歷史申請紀錄 grid**，每列可點擊跳轉**明細畫面**
3. 「查詢」依條件過濾寫入 grid；「新增」跳轉**新增表單頁**，送出後直接跳該單明細
4. 明細畫面顯示完整欄位與接收人/乘客操作（接受、交貨、上車、完成），含返回查詢

> 正式版技術棧仍為 .NET Framework 4.8 / ASP.NET MVC（見 PLAN.md 第 1 節）。
> 本原型僅為流程與規則的互動驗證，資料存於記憶體，重新整理頁面即重置。

## 如何執行

直接用瀏覽器開啟 `index.html` 即可（不需架站、不需安裝任何套件）：

```
open index.html          # macOS
# 或直接雙擊檔案 / 拖入瀏覽器
```

## 專案結構

```
index.html            主框架（側邊導覽 + 頁面容器）
css/styles.css        設計系統（沿用需求報告視覺語彙）
js/data.js            主檔與示範資料（據點/站點/車輛/司機/係數/保修/請假）
js/loadengine.js      共用裝載判定引擎（VD.Core 對應，Phase 1）
js/moduleA.js         模組 A：區域內物流媒合
js/moduleB.js         模組 B：南北幹線貪婪派車
js/moduleC.js         模組 C：差旅共乘批次媒合
js/app.js             前端控制器（導覽、渲染、互動）
docs/                 PLAN.md 與三份原始需求報告
```

## 已實作的核心邏輯（對應 Guardrails）

### 共用裝載判定引擎（G01–G05）
- Level 1 有效體積加總（乘貨物類別浪費係數）
- 地板面積瓶頸法 + 長寬比形狀懲罰係數（G02）
- Level 2 單品六方向旋轉維度檢查（G01）
- 重量累計檢核（G05）
- `WasteFactorProvider` static 單例 + 記憶體快取 + 保底值（G03/G04）
- 回傳含失敗原因碼（L1_VOLUME / FLOOR / L2_DIM / WEIGHT）與逐步 trace

### 模組 A：區域內物流（G10–G20）
- 10 站固定路線、固定地理順序、無貨跳過
- 時間軸最近班次媒合、裝不下 pass 下一班、當日末班仍不行→「請明天請早再試」（G10–G12）
- 站內時間額度逐張判定、額度不足跳過→順延（G16/G17）
- 收貨時間二選一：指定期望時間（到站差最小）/ 越快越好（G19）
- 駕駛異常回報：標異常站點→記錄到申請單層級→立即自動寄信（申請人＋直屬主管，一單一信 G20）

### 模組 B：南北幹線（G30–G44）
- 10 據點南北固定順序（G30）
- 非直達貪婪終點判斷：容量或總計時間任一觸頂即終點（G32/G33/G35）
- 直達獨立派車、單一目的地、純容量加總（G38/G39）
- 回程固定回出發據點、全域直達鎖定、動態淨值延續、被排擠自動順延（G36/G40/G41/G42）
- 完整五列派遣模式決策矩陣（3.7），派車後標示本趟落點
- 天數對照表查表（直達／有停靠兩張表，示意值 P1）（G37）
- 調度室顯示派遣模式與觸發原因、路線視覺化（G44）

### 模組 C：差旅共乘（G50–G63）
- 來回單／單程單分兩條分支，不互相混合（G50）
- 批次媒合按鈕：未來 7 天、已成功單不重排（G53）
- 自動媒合條件完全相同比對（G54）；最晚抵達僅參考不參與（G55）
- 資源可用性檢核：車輛保修排除、司機請假時段重疊比對、工時 20:30（G52/G60/G61）
- 單程單 4 小時窗配對、等待計工時（G51）
- 手動併車：前後 1 天已派車候選、不篩目的地、完成合併即成立（G56）
- 逾期自動作廢：通知申請人、紀錄保留、不轉人工（G57）
